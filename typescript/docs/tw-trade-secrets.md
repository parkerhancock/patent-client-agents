# Taiwan Trade Secrets Act

October 22, 2026. The TypeScript library serves the Taiwan Trade Secrets Act
(營業秘密法) in the official English translation published by the Laws &
Regulations Database of the Republic of China. All 25 Articles, as amended
January 15, 2020, ship inside the client package and are indexed into an
in-memory SQLite/FTS5 database on first use. There is no corpus file, path
variable, download or API key. The MCP adapter uses a separate `tw:read` scope
for HTTP access.

| Library client | MCP tools | Status resource |
| --- | --- | --- |
| `TwTradeSecretsClient` | `search_tw_trade_secrets`, `get_tw_trade_secrets_section` | `tw-trade-secrets://corpus/status` |

Tool names and parameters match the Python connector (`query`, `limit`,
`offset`, `syntax`, `sort`, `full` for search; `citation` as a string or list
for get). The curated facade routes `search_legal_reference` and
`get_legal_reference` with `corpus='tw_trade_secrets'` to the same code, as the
Python facade does. Python registers no status or usage resource for this
connector; the status resource is new.

## What Python actually serves

Python's builder (`patent-client-agents-build-tw-trade-secrets-corpus`) never
fetches anything. It loads `tw_trade_secrets/data/seed.jsonl` (SHA-256
`29bec8c78be1894d4aa540355e4a6101f0508728e5248dd1bf2be45186e4614b`), seven
records for Articles 1, 2, 3, 10, 11, 13 and 13-1, into SQLite at
`TW_TRADE_SECRETS_CORPUS_PATH` or `~/.cache/patent_client_agents/tw_trade_secrets.db`.
The deploy image sets no such variable, the Dockerfile builds no such file and
`gs://patentclient-mcp-corpora/manifest.json` has no entry for it. On October
22 the hosted server answered `search_legal_reference` for this corpus with
"TW Trade Secrets corpus not found at /home/law-tools/.cache/...". The
deployed connector serves nothing.

The seed is also not the official translation, although its docstrings say it
is. Compared with the official page, only Article 2 is close to verbatim. The
others are paraphrases with different substance:

- Article 11 in the seed grants "an injunction ... and may also claim for
  damages". The official Article 11 provides removal and prevention of
  misappropriation and destruction of infringing items; damages are in Article
  12, which the seed omits.
- Article 13 in the seed refers to "damages under Article 11" and lists three
  methods, including a reasonable royalty. The official text has two methods
  (Civil Code Article 216 with a lost-profit fallback, or the infringer's
  profits) plus up to three times proven damages for intentional acts. There
  is no reasonable-royalty method.
- Article 10 in the seed lists three acts of misappropriation; the official
  text lists five and defines "improper means".
- Article 13-1 in the seed omits the four enumerated acts, attempt liability
  and the gain-based fine increase.
- Article 3 omits the second paragraph on non-employment inventions, and the
  seed's article titles ("Calculation of Damages", "Criminal Liability" and so
  on) are not in the official translation, which has no captions.

Because Python serves nothing and its seed is unreliable, this port does not
use the seed or a Python-built database.

## Source, bundling and refresh

The data module `packages/client/src/tw-trade-secrets-data.ts` is generated by
`scripts/build-tw-trade-secrets-data.ts` from one plain HTTP GET of
<https://law.moj.gov.tw/Eng/LawClass/LawAll.aspx?pcode=J0080028>, with no
browser, cookies or challenge handling. The retrieved page is archived
gzipped at `tests/fixtures/tw-trade-secrets/J0080028-en.html.gz` with its
receipt in `source.json`:

| Retrieved | Page bytes | Page SHA-256 | Amended date | Database "last update" | Articles |
| --- | --- | --- | --- | --- | --- |
| 2026-10-22T11:17:17Z | 43,808 | `6936ffafdc0d4f516655c6f3d5da1ade1a6e610b52afcf791a1095de1d6cf32a` | 2020-01-15 | 2026-10-16 | 25 (1-16, 13-1 to 13-5, 14-1 to 14-4) |

The parser takes each `col-no`/`col-data` row, turns `<br />` into newlines,
decodes entities and trims each line; it does not otherwise touch the text.
It fails if the title, amended date or any article row is missing. The
official page itself hard-wraps three items of Article 10 mid-sentence
("the preceding\nitem"); those breaks are kept as published.

To refresh, from `typescript/`:

```sh
bun scripts/build-tw-trade-secrets-data.ts --fetch
bun run format
bun test tests/tw-trade-secrets.test.ts
```

`--fetch` rewrites the archived page and receipt; without it the script
regenerates the module from the archive after checking its hash. Review the
diff of the data module before committing; a change in `amended_date` means
the Act was amended.

Bundling was chosen over a corpus artifact because the whole Act is about
18 KB of source, smaller than the zstd framing and pin machinery an artifact
would need, and it works unchanged in Bun, Node and browsers. The FTS index is
built once per client from the bundled rows with the official SQLite
WebAssembly build (`openBuiltDatabase` in `runtime/sqlite.ts`, new in this
port), using Python's schema and `porter unicode61` tokenizer without the
always-null title column. `get_tw_trade_secrets_section` does not need the
index at all.

## Behavior and Python differences

- `corpus_version` keeps Python's `snapshot-<date>` form, but the date is the
  retrieval date of the text. Python's date was the day the SQLite file was
  built, which said nothing about the text. `corpus_synced_at` and
  `retrieved_at` are the retrieval timestamp; status and section items also
  carry `amended_date`.
- `title` is always null; it stays in the item shape so Python consumers keep
  working.
- Every query term is quoted as FTS5 text. Python left bare words unquoted, so
  `NOT` alone and `damages AND` raised FTS5 syntax errors and `OR`/`NEAR` ran
  as operators.
- `sort='outline'` is statutory order (2, 3, ... 10, 13, 13-1, 14). Python
  sorted the section strings, giving 1, 10, 11, 12, 13, 13-1, ..., 2, 3.
  Relevance ties fall back to statutory order so pages are stable.
- Citations accept Python's forms ('Art. 2 Trade Secrets Act', 'Section 13
  Trade Secrets Act', 'Art. 13-1', bare '13-1') and also 'Art.13', '§ 13',
  'Trade Secrets Act Art. 10', 'Taiwan Trade Secrets Act, Article 12' and
  en-dash sub-numbers ('13–1'), all of which Python rejected.
- A list passed to `get_tw_trade_secrets_section` puts unparseable entries in
  `not_found`; Python failed the whole list on the first one. A single missing
  or unparseable citation is still an error, as in Python.
- In the curated facade, an omitted `syntax` means all terms for this corpus,
  as the parameter description says ("statutes='and'"). Python's facade always
  sent its `adj` default, so statute searches ran as phrases. Other corpora keep
  `adj`.

## Verification

[Tests](../tests/tw-trade-secrets.test.ts) check that the bundled module equals
what the parser produces from the archived page and that the page matches its
recorded hash, citation parsing, get, stemmed search, snippets, operator
quoting, syntax modes, outline order and paging, status, cancellation, both
MCP tools (lean and full hits, list order, `not_found`, Python's summary
strings), the status resource, the curated facade route and its default
syntax, and the `tw:read` scope on the authenticated HTTP listener. Node and
headless-Chromium smoke runs search the bundled text. All run offline.

As a parity check, Python's builder and reader (patent-client-agents 0.30.0)
were run over a seed made from the same 25 official Articles. For six queries
across `and`, `or` and `adj`, the TypeScript reader returned the same sections
in the same order with identical snippets. The same Python run confirmed the
`NOT` and trailing-`AND` errors, the string outline order and the rejected
citation forms. The live facade probe (`bun run verify:facade-live`) has a
search and an Article 13-1 case for this corpus; both passed on October 22.
Nothing is deployed.
